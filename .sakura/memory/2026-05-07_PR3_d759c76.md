## 2. 发现的模式

### 代码模式
- **静默降级倾向**：多处使用 `?` 或 `.ok()?` 返回 `None` 而不记录日志，形成了一种“宁可不出错也不报错”的防御风格。
- **缓存设计模式**：`Mutex<HashMap<K, CacheEntry<Arc<T>>>>` 但实际用了 `Clone` 而非 `Arc`，存在从共享到独占的不一致转换。
- **字符串处理模式**：大量手工构建 URL（`format!`）和手动映射英雄名，缺少统一的名称规范化工具函数。

### 架构观察
- **同步 HTTP 阻塞**：整个 adapter 层是同步的，可能阻塞调用线程。若未来集成到 GUI 事件循环中，会产生界面卡顿风险。
- **模块职责分离清晰**：`community_dragon` 独立于 `LocalLeagueClient`，依赖倒置做得不错。
- **外部依赖脆弱性**：CommunityDragon 是 Riot 的静态 CDN，无版本协商机制，URL 硬编码（如 `/latest/`），未来可能失效。

## 3. 规范完善建议

### 建议新增审查规则
1. **外部数据源版本兼容性检查**：当 PR 引入对无版本 API 的依赖时，要求设计回退或自描述机制。
2. **静默失败强制日志**：所有 `ok()?` 或 `.unwrap_or(None)` 类的静默失败，在模块边界必须有 `log::warn!` 或 `debug!`。
3. **并发缓存模式检查**：缓存命中时若包含深拷贝（`Clone`），应标记为潜在性能问题并建议使用 `Arc`。
4. **浮点值用户可见性检查**：格式化后暴露给 UI 的浮点数必须处理 `NaN/Inf`，建议输出本地化友好的占位符。

### 项目特有规范要点
- **一致性要求**：所有新增 adapter 必须与现有 `LocalLeagueClient` 的错误处理风格一致（即均不 panic，返回 `Option`/`Result` 并记录日志）。
- **英雄名称规范化工具**：建议抽取 `normalize_champion_name` 公共函数处理多词、撇号、罗马数字等。

## 4. 经验教训

### 未来审查关注要点
- **名称映射类缺陷**：当代码中出现手工维护的英雄/物品名称列表时，优先检查是否遗漏常见值（尤其是空格、连字符、数字后缀）。
- **缓存与所有权**：审查缓存实现时，注意区分“共享只读”和“独占修改”场景，`Clone` 往往意味着性能隐患。
- **外部 CDN 依赖**：任何新增的 `https://raw.communitydragon.org/...` 类 URL，都应检查是否有本地回退或版本固定。

### 技术/模式审查经验
- **Rust 中 `Mutex::lock().ok()?` 模式**：这是“静默中毒恢复”的一种写法，但通常应该使用 `unwrap_or_else` + 日志，而不是简单地返回 `None`。
- **浮点格式化陷阱**：`round() as i64` 对于 `f64` 超过 `2^53-1` 时精度已丢失，但在此场景（游戏数值）几乎不可能触发，属于“理论正确但实践可忽略”的问题——审查时可以根据项目领域调整严格程度。
- **测试覆盖的盲区**：该 PR 测试覆盖了正常路径，但未测试 CommunityDragon 服务不可用、返回非 JSON、英雄数据缺失等实际故障场景。未来应要求增加故障注入测试。
